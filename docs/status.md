# Phone Remote status (as of 2026-09-03)

Single source for what is built, what is proven, and what is left. Update it in place; do not append a diary. Scope and gate definitions stay in `docs/iphone_ble_remote_mvp_scope.md` (section 7). Rules and invariants live in `docs/worker_learnings.md`. Where the time goes, how to measure it, and the remaining speed experiments live in `docs/latency.md`.
Hardware: dliao's iPhone 15 Pro Max (iPhone16,2) on iOS 27.0 beta (24A5380h); Apple silicon MacBook Pro (M1 Max) on macOS 27.0 beta; Xcode 27.0 beta (27A5252f), Swift 6.4.
No secrets, team IDs, UDIDs, QR payloads, keys, typed text, transcripts, or audio ever go in this file.

## 1. Where things stand

- Automated baseline is green. Last full run (2026-09-03): shared 39/39, macOS 122/122 (2 skipped), iOS simulator 116/116, plus the 2,000-input decoder corpus. First green five-target build and test loop: 2026-09-02.
- The project is generated by `scripts/generate_fallback.py` (XcodeGen is not installed). Six targets: `PhoneRemoteShared`, `PhoneRemote-iOS`, `PhoneRemote-macOS`, and three test bundles. Swift 6 with `SWIFT_STRICT_CONCURRENCY=complete`.
- Signed install and launch on the physical iPhone works (first proven 2026-09-02). The phone currently carries bundle `com.davidliao.phoneremote.ios`, which is now the default prefix in the generator, `project.yml`, and the phone scripts, so no environment variable is needed.
- iPhone log collection (`scripts/logs-phone.sh`, sysdiagnose) is blocked by Xcode 27 `CoreDeviceCLISupport.DiagnoseError error 0`. Workaround: the in-app `IPhoneDebugLog` pulled by `scripts/debug-phone.sh`.
- The Mac app lives at `~/Applications/PhoneRemoteMac.app`, signed locally, Accessibility granted (2026-09-02). It serves a loopback debug API at `http://127.0.0.1:18765/state` and `/health` and writes `/tmp/phoneremote-mac-debug.json`.
- In-app QR pairing was observed end to end on hardware once (2026-09-02, Mac showed `Paired with <phone name>`, Keychain trust record present). Later BLE and reconnect changes broke it several times; fixes landed with tests, but a fresh hardware QR-to-paired run after the last fixes is not recorded.
- The iPhone camera preview was black from 2026-09-02 to 2026-09-03 across 18 code attempts, and on 2026-09-03 push-to-talk twice streamed all-zero audio (`ptt_frame peak=0`) through working code. Root cause for both: the owner's debug mode mirrors the iPhone screen onto the Mac, and iOS blocks the camera and microphone system-wide while the screen is captured (`app_init`/`ptt_press` log `screenCaptured=yes`; the built-in Camera and Voice Memos apps are dead too). Stopping the mirror or restarting the phone frees them. The app now warns on press when the mic is blocked this way. See `docs/postmortem_camera_black_preview.md`.
- Reconnect after a Mac app restart is fixed 2026-09-03: the phone drops its session when the link goes back to advertising (`session_lost`) and re-handshakes on the next ready (verified: paired again 3 s after the Mac relaunch). The Mac polls `retrieveConnectedPeripherals` once a second while scanning, because a phone the system already holds a link to never appears in a scan; the same tick now enforces the connection timeout, which the shipping app never ran before.
- Ping and trackpad on hardware were dead after pairing once (Mac ignored a repeated hello). Fixed 2026-09-02 (Mac accepts a new control hello while paired; phone marks paired on finish sent). Physical ping/trackpad result after the fix is not recorded.
- Air mouse is wired end to end (Core Motion, `motionPointerDelta`, Mac pointer injector). It is a Settings toggle (`airMouseEnabled` in UserDefaults) rather than a hold-to-activate clutch since 2026-09-03; while it is on it tracks whenever the Trackpad screen is showing and the link is ready, so pointing and tapping work together. The old `AirMouseClutchButton` and the Air Mouse segment of the control picker are gone. Axes inverted, default speed 2400, slider 500 to 6000, dead zone 0.0004 rad per sample (was 0.002, which swallowed anything slower than about 11 deg/s). Smoothness work 2026-09-03: it shares the trackpad's compact frame, its 16 ms pacer (about 60 cursor updates a second, was 25), and `CursorTravel`, which carries the sub-point remainder that per-packet rounding used to discard. Gain is a bounded curve around 30 deg/s instead of a straight line. See `docs/latency.md`. Trackpad has its own speed slider (0.5x to 4x). Both sliders persist in UserDefaults. Physical feel, drift, and 32 px target checks are not recorded.
- Push-to-talk voice typing is implemented as a live IMA ADPCM stream (PRA1 start/data/end frames) into a local `nemo-speech` realtime WebSocket (Swift client, one connection per utterance, no Python; punctuation comes from Nemotron), cleaned up by "S1-mini" by "Superwhisper" on the local Ollama, typed through the safe text path. Reworked 2026-09-03 after a skeptical audit: the phone runs capture, 40 ms chunking, ADPCM, encryption and fragmentation on one serial voice queue with a warm audio engine (start frame before the mic, end frame before mic stop, whole-message drops with sequence gaps, interruption and background handling); the Mac streams PCM to the server as frames arrive, commits on end or 1.5 s idle, and types finals in start order. Latency fix (2026-09-03): the phone holds the audio session and engine open for the whole foreground session (`prewarm` on foreground and on permission grant, `playAndRecord`/`mixWithOthers` so other audio keeps playing, no preferred hardware rate), so a press only attaches the sample handler instead of paying 250-400 ms of session activation; the session is handed back on background, interruption and route change. The button fires a prepared haptic on touch down and a lighter one on release, now through `Haptics`. It still holds the mic 150 ms after the finger lifts (`releaseGrace`) and seeds mic permission at launch; the Mac pads 400 ms of silence before commit (final text lands about 700 ms after commit for real speech). `ptt_first_audio.ms` in the phone log measures press-to-first-audio. Holding also shows two trash targets in the bottom corners (2026-09-03): dragging the finger into one arms it, releasing there drops the buffered audio, ends the stream with the new `.cancel` flag, and the Mac tears down that recognizer without typing anything; dragging back out restores the normal path. Hardware check of the corners is not recorded. Experimental spoken edits landed 2026-09-03, off by default behind the phone's "Edit text with a spoken instruction" setting: two pencil circles sit above the trash ones, an armed edit sends an `.intent` frame so the Mac holds its typing and warms the model, and the release ends the stream with `.edit`. The words become an instruction, never typed; the Mac sends the focused field plus the instruction to `qwen3:4b-instruct-2507-q4_K_M` on the local Ollama (five-shot, temperature 0, weights kept resident, `PHONE_REMOTE_EDITOR_MODEL` to override) and applies the answer as Select All plus one insert, so Cmd+Z undoes it in one step. The field is left untouched when it is empty, unreadable, over 1,200 characters, unchanged by the model, or the model fails; `merge` in `/state` says which. Measured on this Mac: 0.2 to 0.8 s per edit once loaded, about 3 s on the first one. Known weakness: an instruction with two parts is sometimes only half applied. Hardware check is not recorded. Proven on hardware 2026-09-03: a spoken sentence was typed on the Mac (`Typed spoken text`, 0 missing chunks).
- End-to-end latency is now measurable from inside the apps (2026-09-03). The phone's Settings tab has Ping Mac: five pings 250 ms apart reporting average, best, and how many returned, also logged as `ping_rtt`. The Mac reports `keyPostMs` in `/state` for the last paced key burst. First measurement: Bluetooth round trip 53 to 85 ms, average 68, so roughly 30 ms one way, and that hop is now the largest single cost. Key posting was 40 ms flat per gap and is now `modifierSettle` 0 ms plus `keyGap` 10 ms. Every stage also keeps a rolling window since 2026-09-04: `/state` carries a `latency` array of seven Mac probes, and the phone logs a `latency` event every five seconds with seven more. Method and numbers: `docs/latency.md`.
- Cursor latency work landed 2026-09-03 for both the trackpad and the air mouse. Deltas travel as a compact binary `PointerStreamFrame` (about 87 wire bytes against 282 for the JSON envelope), the phone keeps and retries the summed travel when the radio is busy instead of dropping it, the gesture engine's second rate limiter is gone so `CursorMixer` is the only pacer, cursor traffic no longer rebuilds the Mac debug snapshot on every packet, and the Mac no longer hops every received frame through `Task { @MainActor }`. The whole latency picture, the measurement method, the measured numbers, and the remaining experiments now live in one place: `docs/latency.md`. Physical cursor feel after these changes is not measured yet.
- Holding a delete key and sliding is an experimental Settings toggle (`deleteScrubEnabled`, off by default, 2026-09-03). A tap on either backspace key still sends exactly one key and one message. Holding and sliding left rubs out one notch per 24 pt of travel with a selection tick for each; sliding back restores them with a softer thud, and the key shows the running count. `DeleteScrubTracker` is a ratchet: it measures travel from where the last notch was taken, not from where the finger landed, and floors the count at zero. Measuring from the start was the first thing that made restore look broken (2026-09-03): a slide that ran past the last word spent notches on nothing, and coming back had to retrace every one of them before a word reappeared, which is further than the glass is wide. The count can still read higher than what the Mac managed to erase, because only the Mac knows where the text ran out; both keys share it and differ only in the `DeleteScrubGranularity` they send. Restore needs the text, which the phone cannot know, so the new reliable `deleteScrub` message (type 16, begin/delete/restore/end) is served on the Mac by `DeleteScrubCoordinator`. It reads the field once, through the new `AXFocusedTextReader.textAroundCaret`, as the press starts erasing, and every notch after that is served from that one reading: a notch works out how long the run it wants is, presses plain Delete exactly that many times, and pushes the characters it took onto a stack. Restore pops the top and types it back. Nothing is asked at the turn and nothing is measured, so what comes back is character for character what went, and a restore run cannot invent text or repeat itself. Unlike the voice path's `focusedText`, that read does not insist the caret be at the very end, which was the second thing that made restore look broken (2026-09-03): a slide past the start of a line leaves the caret elsewhere and every restore was refused with `caretNotAtEnd`. Only the text in front of the caret is read, since that is all a delete key can touch. Reads that fail are capped at six per press, and a single failed read is retried by the next notch rather than ending the slide, which was the third thing that made restore look broken. The fourth was Electron, found by testing in the Claude desktop app (2026-09-04), and it is what settled the design: earlier versions pressed the app's own Option and Delete for a word notch and then asked the field what had left, and Chromium will not answer. It hands back a container element for a contenteditable, and a container does not track the caret, so it reports `kAXSelectedTextRange` as {0, 0} while its value holds the whole field, which reads exactly like a field that was emptied. The trail showed it as `rebased:h20-0,t0-20` and then `range:zero` on every read after, so it is persistent rather than intermittent and no retry helps. Counting its own plain Delete presses is the one measurement no app can get wrong, so the Mac now decides where a word ends itself: skip trailing whitespace, then take the run of letters and digits, or the run of punctuation, which is close to what Option and Delete does in a Mac text field (`foo.bar` gives up `bar` and leaves the dot). The cost is that own word rule; the presses themselves are close to free, because a notch is one `hotkeyRun` command carrying the whole run and `keyRunGap` is zero (2026-09-04). Pacing each press separately was the first cut, and at 20 ms a character it made the text visibly trail the finger. The worry that unpaced identical keys would be coalesced or read as a key repeat turned out to be unfounded, and was settled by measuring rather than reasoning: the new `/keyburst?count=N` endpoint types its own filler into the focused field, presses Delete N times in one run, and reports how many characters actually left. It is exact at 8, 20, 40 and 64 presses in a native text area, and at 20 and 64 in a Chromium textarea, five times over. See `docs/latency.md`. A run is bounded by `InputPolicyLimits.maxHotkeyRun` (64), which a notch clamps itself to so it never builds the one thing the policy would turn down, and the run never travels the wire: the phone cannot ask for it, and `SharedInputProtocolAdapter` refuses to encode it. A slide that runs past the start of the text presses nothing at all, so overshooting is free and everything it did erase still comes back. `textAroundCaret` also refuses a caret at location 0 in a non-empty field (`range:zero`), since a caret genuinely at the start has nothing in front of it for a delete key to take. Secure input is never read from and never typed into, checked on both sides like `VoicePTTCoordinator` does. Every event still goes through `SafeInputInjector` and the same policy checks. A field that will not answer (a terminal, a secure box, an Electron container) falls back to the plain key the phone would have tapped, with nothing to restore. Losing the link abandons the press, and `/state` carries the last slide's notches as counts and outcomes only. Covered by `Tests/iOS/DeleteScrubTests.swift` and `Tests/macOS/DeleteScrubTests.swift`; feel on hardware is not recorded.
- Haptics are one module (`iPhone/Haptics/Haptics.swift`, 2026-09-03): press, release, gesture began and ended, and one step for walking a continuous control. Wired to the hotkey bar, the app switcher, push to talk, the keyboard toggle, the pairing buttons, and both experimental scroll gestures taking or releasing a finger. Confirmed on hardware after the audio-session trap below was fixed.
- Trusted reconnect without QR is implemented on both sides with tests. A physical pair-then-relaunch reconnect is not recorded. Every fresh `devicectl install` can wipe the phone's Keychain trust store, forcing a new QR.
- All gate records in `docs/verification/` are `NOT RUN` or `BLOCKED`. `go-no-go.md` says BLOCKED.
- App Store submission blockers cleared 2026-09-05, ahead of any review: the iOS target now ships an app icon (`iPhone/Resources/Assets.xcassets`, single 1024 px, no alpha), a privacy manifest (`iPhone/Resources/PrivacyInfo.xcprivacy`, declaring UserDefaults `CA92.1` and system boot time `35F9.1`, no tracking, no collected data), `ITSAppUsesNonExemptEncryption=false` in `Config/iPhone-Info.plist` (CryptoKit is encryption inside the OS, so the export filing is exempt), and the real `com.davidliao.phoneremote` prefix on every target. The Settings debug-log panel and every `IPhoneDebugLog` write are now behind `#if DEBUG`, so a Release build carries neither the screen nor the log file; the fallback generator never defined `DEBUG` at all before this, so no `#if DEBUG` in the tree could ever have worked. The "Experimental" Settings header is now "Extra features". Still open before a submission: the reviewer cannot run the app without the Mac companion and the local speech and Ollama servers, and every gate in section 2 is unrun.
- Apple's on-device transcriber is a second voice route, off by default (2026-09-06, `iPhone/Audio/OnDeviceTranscriber.swift`). `OnDeviceVoice` is a facade that works on every OS the app runs on and reports `.unsupported` below iOS 26; `AppleSpeechEngine` behind it drives `SpeechAnalyzer` plus `SpeechTranscriber` (`.progressiveTranscription`), feeding the same 16 kHz mono chunks the ADPCM path uses, converted to `bestAvailableAudioFormat`. Boost phrases go in through `AnalysisContext.contextualStrings[.general]`, which is Apple's answer to Nemotron's `speech_contexts`/`boost` list; the list is typed by the owner in Settings, since the Mac's `ScreenVocabulary` walk has no way to reach the phone (there is no Mac-to-phone `MessageType` for it, and with no audio on the wire the Mac gets no signal to walk on). The finished sentence leaves through `typeText`, so the Mac types it as ordinary keyboard text and needs neither `nemo-speech` nor Ollama. `VoiceRouteSettings` is the lock that lets the voice queue read the route the main actor writes. The spoken-edit pencils are forced off while this route is on, because only the Mac can read the field an edit rewrites. `NSSpeechRecognitionUsageDescription` added to `Config/iPhone-Info.plist`. Covered by `Tests/iOS/OnDeviceVoiceTests.swift`; quality against Nemotron on real speech is not measured yet, and that comparison is the whole point of the toggle.
- Git: the whole tree was first committed on 2026-09-03 as `checkin`. Commit small changes with real messages from here on.
- `AUD-003` deviates from the backlog: there is no Apple `Speech` framework adapter anywhere; transcription is the local Nemotron server. Treat that as the accepted design unless the owner objects.

## 4. Known problems and traps

Build and project
- Xcode 27 rejects `xcodebuild -target ... -derivedDataPath`. Always pass `-scheme`.
- `scripts/generate.sh` deletes and recreates `PhoneRemote.xcodeproj`. Never run two generators at once; they race on `xcshareddata/xcschemes`.
- In the fallback generator, give groups repository-relative paths only. Mixing physical and relative paths produced `Shared/Shared/...` duplicates.
- Shared framework must pin `IPHONEOS_DEPLOYMENT_TARGET=18.0` and `MACOSX_DEPLOYMENT_TARGET=15.0` or Xcode 27 picks a newer SDK and the apps cannot link it.
- Test bundles need `ENABLE_TESTABILITY=YES` on the app plus `TEST_HOST` and `BUNDLE_LOADER`, or they compile and fail to link.
- Both app plists need `CFBundleExecutable=$(EXECUTABLE_NAME)`. Without it the simulator install fails with `MissingBundleExecutable`.
- App module names are `PhoneRemote_iOS` and `PhoneRemote_macOS`. XCTest imports must match.
- The framework install name must be `@rpath/PhoneRemoteShared.framework/PhoneRemoteShared`, and app `LD_RUNPATH_SEARCH_PATHS` must include `@executable_path/Frameworks` (iOS) and `@executable_path/../Frameworks` (macOS). Without both the app dies at launch while `devicectl` still reports launch success.
- The repo lives under iCloud Documents. `DerivedData` there picks up Finder tags that break `codesign`. Use `PHONE_REMOTE_DERIVED_DATA=/tmp/PhoneRemotePhoneInstall` (or any `/tmp` path) for device builds.
- Device builds must set `ENABLE_DEBUG_DYLIB=NO`. An unsigned Xcode debug or preview dylib inside the bundle makes iOS kill the app on open. `install-phone.sh` and `install-mac.sh` already pass it; the installer signs every Mach-O then the app.
- The `.serena/` directory and `scripts/__pycache__/` are tool residue, not project code.

Signing and device
- Signing is opt-in: `PHONE_REMOTE_SIGNING=1` plus `PHONE_REMOTE_DEVELOPMENT_TEAM` (optional `PHONE_REMOTE_CODE_SIGN_IDENTITY`, default `Apple Development`). Missing values fail before any device call. Never commit them.
- Pass the phone as an explicit destination (`platform=iOS,id=$IPHONE_UDID`). A generic device build can pick a profile for a different phone and fail at install.
- `xcodebuild` from a non-GUI shell sometimes cannot see the Xcode account. Recovery used once: sign the built app in place with the local identity and existing profile, then `codesign --verify --deep --strict`, then `devicectl device install app`.
- The phone must be unlocked on screen for DDI. `unlockedSinceBoot=true` is not enough; a locked phone returns CoreDevice 12040. `device info ddiServices` must show `isUsable: true`.
- `security find-identity -v -p codesigning` is the quick check for a local signing identity.
- The installed bundle is `com.davidliao.phoneremote.ios`. Pass `PHONE_REMOTE_IOS_BUNDLE_ID=com.davidliao.phoneremote.ios` to `launch-phone.sh` and `debug-phone.sh`, or `debug-phone.sh` prints `STATE_MISSING`.
- `debug-phone.sh` copies by device name (`PHONE_REMOTE_DEVICE_NAME`, default `dliao's iPhone`), not UDID.
- A fresh `devicectl install` often gives the app a new container and wipes the phone Keychain trust store. Expect a new QR after every reinstall.

Mac app and Accessibility
- macOS grants Accessibility to an exact path and signature. Only `~/Applications/PhoneRemoteMac.app` counts. Never `open` a `/tmp` or DerivedData `PhoneRemoteMac.app`; it looks granted while the live app stays denied. Use `scripts/install-mac.sh`.
- `AXIsProcessTrusted()` stays false for adhoc-signed Debug builds with the debug dylib stub. Sign with the local identity after copying (Finder metadata blocked signing during the build step).
- `MacRemoteAppModel` must call `MacLifecycleCoordinator` and `SafeInputInjector` directly. Do not add a second pause or status boolean.
- Missing `NSBluetoothAlwaysUsageDescription` made the macOS test host die before XCTest attached. iPhone plist needs camera, Bluetooth, motion, and microphone strings.
- The Mac debug server can be disabled with `PHONE_REMOTE_DEBUG_SERVER=0`. It binds 18765 or the next few ports and records the port in `/tmp/phoneremote-mac-debug.json`.
- `scripts/logs-mac.sh` shows unified logs, but the app emits no pairing events there. Use `/state`.

BLE and pairing ordering rules
- The iPhone never appears in macOS Bluetooth Settings. Pairing is in-app only: Mac shows QR, phone scans and advertises, Mac auto-connects and asks its user to allow the phone. There is no device picker.
- Advertise with `CBUUID(nsuuid:)`. A Foundation `UUID` in `CBAdvertisementDataServiceUUIDsKey` silently drops the service.
- Guard `stopScan`, `stopAdvertising`, `removeAllServices` on `.poweredOn` or Core Bluetooth logs `API MISUSE`.
- After an unpaired connect or discovery failure the Mac must resume scanning. After a ready disconnect it must rescan for trusted reconnect.
- The 3 second advertise pulse must refresh in place. Calling `stopAdvertising` mid-connect drops the link. Pulse is a no-op while publishing, connected, or ready.
- An advertise error must not tear down a live beacon. The Mac keeps its QR offer if hello never started.
- "Waiting for Bluetooth" is not powered-off. Treating it as off killed advertising before it could start.
- The Mac must accept a new control hello even when it believes it is already paired, answer hello while still subscribing, and keep a live session if a later hello arrives. The phone marks itself paired as soon as finish is sent and forwards Mac control writes without a matching subscriber id.
- QR scan never stops Bluetooth. Any advertising pause waits for the camera's `onStarted`. Opening the camera pauses saved-Mac reconnect until the Mac answers; Cancel, a decline, or the code expiring resumes it. A QR handshake failure stays on the QR path and never falls back to old trust.
- `KeychainTrustedDeviceStore` keeps every trust record in one Keychain item (account `trusted-devices`) holding a JSON array. Never fetch many records with `kSecReturnData` plus `kSecMatchLimitAll`; that returns `errSecParam` on macOS and the menu bar shows "Pairing storage is unavailable". One item also means one approval prompt per read instead of one per paired phone.
- Keep BLE-ready and authenticated separate in every UI and snapshot. `MacPairingProgress` is presentation only.
- The QR pairing ID is the trust-record device ID on both sides.

Camera and audio
- When a camera or mic feed looks dead, open the built-in Camera app first. If it is dead too, restart the phone. Do not touch app code. `screenCaptured=yes` with nothing mirroring plus constant `luma=16` means iOS muted the feed.
- Scanner: back wide camera, `.high` preset, preview layer attached in init, one output (QR metadata), `automaticallyConfiguresApplicationAudioSession=false`, 2x zoom after configuration. Do not reintroduce a frame tap, deferred-start calls, the virtual triple camera, a SwiftUI `clipShape` over the preview, or a full-screen shell.
- iOS mutes the Taptic Engine for any app holding a recording session, and this app holds one from launch, so every buzz in the UI was silently dropped until `setAllowHapticsAndSystemSoundsDuringRecording(true)` was set after the category. Setting a category resets it. `ptt_mic.haptics` in the phone log reports it.
- Hold to talk owns the audio session and must restore `SoloAmbient` on stop. The capture session never configures the audio session. The `AVAudioEngine` is created only when a press starts.
- App start marks the mic path backgrounded. Foreground must clear it, or press returns `notForeground` and `sent=0`.
- Pro iPhones cannot focus closer than about 20 cm. The scanner hint says 25 cm.

Concurrency and Swift 6
- Static GATT and framing collections need `Sendable` value types. Add conformances to immutable structs and enums only; no `@unchecked Sendable` over mutable state.
- `kAXTrustedCheckOptionPrompt` is a non-Sendable imported global. Use a literal CFDictionary key.
- Core Motion callbacks arrive off main. `MotionPointerSession` hands samples to `CursorMixer`, which sums travel and paces it at 16 ms on the same main turn. Do not add a `Task { @MainActor }` hop; it queued without bound and caused growing lag.
- Motion packets are unreliable; drop extra samples instead of queueing. Unreliable follow-on fragments still enqueue so a message is never half sent.
- Shared code stays transport neutral: no Core Bluetooth, Core Graphics, Core Motion, AVFoundation, or Speech types in `Shared/`.

Transcription helper
- `Mac/Transcription/NemotronRealtime.swift` health-checks `nemo-speech serve` on `PHONE_REMOTE_NEMO_PORT` (default 18766) at launch, spawns `~/.local/bin/nemo-speech` with the Nemotron GGUF from `~/.cache/huggingface/hub` when nothing answers, logs to `/tmp/phoneremote-nemo-speech.log`, and stops the child on quit. Each utterance is one `/v1/realtime` WebSocket; audio streams as it arrives and `.end` (or 1.5 s of silence from the phone) commits.
- `Mac/Transcription/S1MiniNormalizer.swift` posts each final transcript to "S1-mini" by "Superwhisper" on the local Ollama (`PHONE_REMOTE_S1_PORT`, default 11434, model `PHONE_REMOTE_S1_MODEL`, default `s1-mini`) and types the result. It uses `/api/generate` with `raw` set, so the trained system prompt, control line and empty think block live in Swift rather than in an Ollama template. Register the model with `./scripts/install-s1-mini.sh`. Ollama is never spawned: no Ollama, no model, a bad reply, or a slow one past 5 s types the raw transcript instead. Measured 0.1-0.9 s per utterance on the F16 build.
- `Mac/Transcription/ScreenVocabulary.swift` is an experimental word boost, on by default, toggled by "Boost words on screen" in the menu (`screenVocabulary` in UserDefaults). A press is answered at once from `VocabularyCache` and never waits: `AXScreenVocabularyReader` then walks the focused window over Accessibility (600 nodes, depth 12, 0.25 s messaging timeout) on its own queue, one walk at a time, to refresh the cache for the next press. The walk is off the main thread and off the utterance's critical path, so a window that answers slowly costs nothing; the app that has focus is asked through the Accessibility system-wide element rather than NSWorkspace, which has main-thread rules. A token is kept when it is 3-24 characters and either carries a capital (names, acronyms, identifiers, keys shaped like a ten-character uppercase code, all of which are worth being able to dictate) or is lowercase and unknown to `SystemWordDictionary`, which asks NSSpellChecker backwards to find jargon such as `kubectl`; lookups are memoised. The cache holds at most 400 words. Seeing a word on screen, however often, only renews a 600 s lease; actually speaking it is the hit, worth `+1` and three hours on top of whatever is left, so the vocabulary you really use accumulates a long lease while screen furniture falls out. `VoicePTTCoordinator` credits the recogniser's own words, before the normalizer rewrites them, matching case-insensitively; a word that was never on screen is never invented by speech. The top 40 by hits ride on the realtime `session.update` as `speech_contexts: [{phrases, boost: 3.0}]`; the recogniser applies one strength to the whole list and clamps it at 5, and refuses any session update once audio has started. Skipped while secure input is active. The phrases go to the local recogniser only and are never logged. Walk costs measured in place with `/vocabulary?app=<bundle id>` (`cacheHits` counts spoken words, `cacheAdded` counts words a walk filed), no app activated: Claude 17 ms, Chrome 52 ms, Xcode 181 ms with the node budget exhausted, Messages 230 ms, Notes 520 ms in the background and about 2.3 s while focused.
- `Mac/Transcription/FocusedTextField.swift` reads the focused field over Accessibility before normalizing (`AXFocusedTextReader`, 0.25 s messaging timeout, on the main thread) so a second press continues the first instead of starting a fresh sentence. It asks the frontmost app for its focused element rather than the system-wide element, which answers `kAXErrorNoValue` for some apps, and it sets `AXManualAccessibility` on that app when the speaker starts talking: Chromium, and so every Electron app, keeps its accessibility tree off until a client asks by name and then builds it in its own time, which is why voice typing saw no field at all in Electron until 2026-09-03. The whole field plus the new words go to S1-mini as one payload; `TranscriptMerge` then types only what changed, deleting at most 40 characters back so a reworded last sentence can be corrected without rewinding a paragraph. The plain path is kept whenever the field is unreadable, empty, over 4000 characters, has a caret anywhere but the end, or moved while S1-mini was thinking: only the new words are typed then. Field text is display-only and never logged.
- Transcripts are never logged and never appear in `/state`. Debug counters only: `audioFrames`, `audioSamples`, `audioMissingChunks`, `audioPhase`, `audioMerge`, which is `merged`, `appended`, or the reason the field could not be joined, and `audioVocabulary`, the last boost walk as `156ms/183nodes/40words` with `+` when the node budget ran out. `./scripts/debug-mac.sh /focus` reports what Accessibility can see in the focused field right now as roles and error codes, which is how the Electron fault above was found without a phone in hand. `./scripts/debug-mac.sh /vocabulary` runs one boost walk and reports its cost and cache counts; add `?app=<bundle id>` to measure a named app where it sits, since Accessibility reads any running app and nothing has to be brought to the front. It reports counts, milliseconds and a bundle id, never a word it read.

Session crypto and framing
- Replay protection is a 64-slot sliding window that only advances after the AEAD tag verifies (fixed 2026-09-03). A strict high-water mark dropped whichever unreliable frame lost an encryption race between the voice queue and the cursor path. Covered by `Tests/Shared/ReplayWindowTests.swift`.
- Open: the session has no direction binding. `deriveSessionKey` yields the same key on both sides and the authenticated header carries no role, so a captured Mac-to-phone frame replayed at the Mac is rejected only because the phone's sequence counter runs far ahead. That is an accident, not a rule. Fix with per-direction subkeys or a role byte in the header. This also blocks the packet-shrinking work in `docs/latency.md`.
- Open: `PairingSession.maxPlaintextBytes` (8,192) equals the envelope ceiling (8,192), so a maximum-size message encrypts and then always fails fragmentation on the 60 bytes of overhead.
- Open: `PairingSession.decrypt` and `BLEFrame.decode` mix length checks with absolute indices, so a `Data` slice with a non-zero start index would crash instead of throwing. Not reachable today because reassembly rebases the buffer.
- Open: `IPhoneBLEPeripheralTransport.send` calls `updateValue` directly even when the same channel already holds queued frames, so a new cursor frame can jump ahead of a queued voice fragment and break reassembly on the Mac. Single-frame cursor messages never queue, so the cursor path does not trigger it today.

Environment noise that is not a failure
- macOS tests print `com.apple.linkd.autoShortcut` warnings. Simulator prints a Core Motion preference notice. `logs-mac.sh` shows CoreSpotlight and XPC noise. AppIntents metadata warnings appear in builds.
